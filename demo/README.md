# 企业岗位经验 Skill 生成平台

把优秀员工的岗位经验，通过自然语言描述，自动转换为可执行、可评测、可版本管理的 AI 员工能力资产。

> 数花智算 DataAgent 实习生面试题作品

---

## 核心主张

**报告里的每一个数字，都由确定性代码算出，不由 LLM 生成。**

这条主张贯穿全部设计。它的直接后果是：**AI 可能解读错，但绝不会算错。**
而"解读"本来就是主观的，人类专家之间也会有分歧——企业对它的容错度天然更高。

```
analysis_flow 中的步骤分两类：

  🔢 metric 步骤  →  pandas + 受限表达式求值器  →  产出【指标结果表】
                     结果 100% 可复现、可验算、可溯源

  🧠 llm 步骤     →  只接收【指标结果表】，不接触原始数据
                     Prompt 明令禁止计算任何数值
                     职责限定为：归因、解读、给建议
```

再加一道**数字幻觉检测**：扫描 LLM 输出中的每一个数字，凡是指标结果表里不存在的一律标红。

## 快速开始

```bash
# 1. 安装依赖
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt

# 2. 配置 API Key（可跳过，跳过则运行在演示模式）
./.venv/bin/python tools/set_key.py

# 3. 验证 Key 可用（约消耗 $0.001）
./.venv/bin/python -m tests.check_llm

# 4. 启动
./.venv/bin/uvicorn app.main:app --port 8000
```

浏览器打开 **http://localhost:8000**

> ⚠️ 请在地址栏访问上述 URL，不要直接双击 `static/index.html`。
> （即便双击打开也做了兼容，但走服务地址是标准方式）

支持 Anthropic Claude 与任意 OpenAI 兼容接口（DeepSeek / 智谱 / 通义等），
换供应商只需改 `.env` 中的三行，业务代码零改动。详见 `.env.example`。

## SkillSpec：全系统的中心

题目要求的七个字段本身就是一份 Schema。所有模块都围绕它读写。

```python
class SkillSpec(BaseModel):
    # ===== 题目要求的七个字段 =====
    name: str                          # ① Skill 名称
    description: str                   # ② Skill 描述
    use_cases: list[str]               # ③ 使用场景
    input_schema: list[InputField]     # ④ 输入数据定义 —— 数据契约
    analysis_flow: list[AnalysisStep]  # ⑤ 分析流程 —— metric | llm 两类步骤
    agent_prompt: str                  # ⑥ Agent Prompt
    output_template: str               # ⑦ 输出结果模板

    # ===== 治理所需的补充字段 =====
    metric_dictionary: dict[str, str]  # 指标口径显式定义
    metric_units: dict[str, str]       # 展示单位显式声明
    version: str                       # 版本号
    status: SkillStatus                # draft | published | deprecated
```

补充字段不是题目要求的，但没有它们 Skill 无法被"管理"：

- **`metric_dictionary`** —— 企业内部最容易吵架的就是口径。"转化率"到底除以进入人数还是点击人数，两个部门能吵一整年。不显式写死，Skill 一发布就会被质疑
- **`metric_units`** —— 单位也是口径的一部分。「连带率」是 1.4 **件**/单而不是 140%，靠名字猜必然出错
- **`version` / `status`** —— 没有版本就没有回滚，没有回滚就不敢改

## 四道校验闸

"如何避免 AI 生成错误 Skill"的落地实现。防错不靠"让模型更聪明"，靠机制。

| 闸 | 检查什么 | 典型拦截 |
|---|---|---|
| ① 结构校验 | 字段齐全？有没有 metric 步骤？ | 「没有任何 metric 步骤，数值不允许交给 LLM 生成」 |
| ② 逻辑闭环 | 引用的字段都定义过吗？ | 「步骤 S1 引用了未定义的字段『退货订单数』」 |
| ③ 领域规则 | 指标在白名单内？公式可解析？ | 「Agent Prompt 缺少【禁止事项】章节」 |
| ④ 冒烟测试 | 用 mock 数据能真的跑通吗？ | 静态检查全过、运行时才崩的公式 |

**闸④ 存在的意义**：`round(曝光人数, 2, 3)` 语法合法、函数在白名单内、引用的字段也都存在——静态检查无论多严都拦不住它，只有真跑一遍才知道会 `TypeError`。

校验失败时不是盲目重试，而是**把具体错误回喂给模型做定向修正**。实测错误数逐轮递减（6 → 3 → 1 → 0）。

```bash
./.venv/bin/python -m tests.test_validator   # 30 项，每类错误都有可复现的反例
```

## 三层防错的能力边界

实测发现的边界，比声称的能力更重要：

| 层 | 能抓什么 | **抓不到什么** | 处置 |
|---|---|---|---|
| 四道校验闸 | 结构、引用、语法、可执行性 | **语义是否讲得通** | 硬拦截 |
| 模型自检 | 语义错误、口径歧义、边界情况 | **会误报** | 仅提示 |
| 人工确认 | 是否符合本公司实际业务 | — | 最终裁决 |

一个真实案例：生成的 Skill 里出现过

```
人均关闭商机 = 平均销售周期天数
```

语法合法、变量都存在、**四道闸全部放行**——但它把两个毫不相关的概念划了等号。
模型自检一眼抓到了（"混淆了两个无关的维度"），但自检同时也报了一条经核实为误报的问题。

**这就是为什么人工确认环节是特性而不是缺陷。**

```bash

./.venv/bin/python -m tests.run_evaluation    # Golden Set（真实 API，约 $0.05）
```

### Golden Set 五维评分卡

| 维度 | 权重 | 打分方式 |
|---|---|---|
| 数据准确性 | **30%** | 全自动，与人工核算精确比对 |
| 归因合理性 | 25% | 关键词命中 + 瓶颈环节判定 |
| 建议可执行性 | 25% | 关键词命中 + 四要素检查 + 空话反例 |
| 结构完整性 | 10% | 全自动 |
| 表达清晰度 | 10% | 启发式（客套话/篇幅/幻觉数字） |

**发布门槛：总分 ≥ 80 且数据准确性 ≥ 95。**
数据准确性一票否决——数字错了，其他四维得分再高也没有意义。

四组用例特意包含两个"反向"样本：

- **全部达标（负样本）** —— 检验会不会"没病硬说有病"。总在报警的工具和从不报警的一样没用
- **缺必填字段（拦截样本）** —— 检验该拦的时候拦不拦得住，以及有没有说清缺什么、从哪导出

标准答案全部人工独立推导（数据用整数设计，`8000/200000 = 0.04` 可心算复核），
**不取自系统输出**，避免循环论证。

## 关键设计决策

### 为什么 `formula` 不能用 `eval()`

`formula` 是 LLM 生成的字符串，`eval()` 等于任意代码执行漏洞。
引擎用 `ast` 把表达式解析成语法树，再用**节点类型白名单**逐个校验。

```python
x = __import__('os').system('ls')   → UnsafeFormulaError  ✅ 拦截
x = a.__class__.__bases__            → 拒绝属性访问        ✅ 拦截
x = eval('1+1')                      → 未知函数            ✅ 拦截
```

### 为什么多行数据下 `进入率 = 进入人数 / 曝光人数` 是 `sum/sum`

漏斗比率的正确算法是"总和除以总和"，而不是"逐行算比率再平均"。
所以规则是：**裸列名参与算术运算时自动 `sum()` 聚合；需要求平均时必须显式写 `mean(字段名)`。**

### 为什么日期相减要用 `days_between()` 而不是 `-`

隐式类型推断猜对了没人注意，猜错了报出来的是
`unsupported operand type(s) for -: 'str' and 'str'`——生成 Skill 的模型根本看不懂该怎么改。
**显式函数名本身就是文档。**

### 为什么 LLM 步骤要区分 `verify_numbers`

改进建议里天然会出现「把点击率提升至 15%」「素材控制在 30 秒内」这类数字，
它们是**目标值和建议参数，不是数据事实**。对这类步骤做幻觉检测只会产生大量误报。

所以让 Skill **显式声明哪些步骤在陈述事实、哪些在提建议**：

```
S3 漏斗诊断与根因分析  verify_numbers: true   → 严格检测
S4 生成可执行改进动作  verify_numbers: false  → 跳过，并在执行轨迹里标注原因
```

实测误报从 7 降到 0，同时陈述事实的步骤仍在严格把关。

### 为什么幻觉检测的容差必须是绝对值

早期版本用 2% 相对容差，在大数字上会炸开巨大的窗口：
指标「总商品点击人数 9908」的百分比形式 990800，±2% 就是 ±19816，
足以把毫不相干的 999888.77 一并放行——**幻觉检测形同虚设**。

更值得记的是它为什么长期没被发现：测试用例把捏造的大数字和 `47.3%` 写在同一句里，
真正被抓到的只有 47.3，大数字一直漏网，**测试却显示通过**。
现在每个捏造数字都是独立用例。

## 已知限制

诚实地说明边界，比声称无所不能更有价值：

- **数据接入只支持 CSV 上传。** 数据库直连、API 对接、定时调度均未实现——这些对验证核心假设没有帮助，属于 MVP 之后的工作
- **无用户体系。** 单用户运行，没有登录、权限、多租户隔离
- **CORS 全开。** 为了让直接双击 HTML 打开也能用。生产环境必须收紧为域名白名单
- **Golden Set 只覆盖了 1 个 Skill 的 4 个用例。** 另外两个 Skill 尚无评测集
- **关键词打分法有 run-to-run 波动。** 实测同一份数据两次评测，归因维度因模型换了说法而从 100 分掉到 75 分。这也是为什么**唯一的一票否决权给了唯一稳定的数据准确性维度**
- **`metric_dictionary` 是手工维护的 YAML。** 尚未接入企业指标平台
